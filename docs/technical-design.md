# Technical Design

## Architecture

`TelegramBotRuntime` owns Bot API polling, authorization middleware, prompt callback acknowledgement, and the top-level Telegram error boundary. `TelegramGateway` composes the runtime and focused command/application controllers and retains command parsing plus Telegram formatting. `TelegramPickerController` owns restart-safe workspace, resume, model, and background-process controls, including resource-version validation; `TelegramCallbackController` is the single Interaction Control claim/commit/release boundary for approvals, panels, session actions, destructive confirmations, pickers, processes, and legacy controls. Every issued token is opaque, bound to the Controller and Telegram chat, names one intended operation and target resource, expires within ten minutes, and carries an expected resource version when mutable state is involved. `TelegramRouting` owns explicit destination selection: persisted thread-picker controls, one-shot compose state, reply associations, and opt-in per-chat/user sticky routes. `PendingInteractionManager` owns questions, approvals, native permission grants, and MCP forms: opaque callbacks, persisted drafts, schema-typed protocol values kept separate from display labels, validation, and single-submit transitions. While a draft awaits text, the manager consumes that route across pending, submitting, failed, expired, stale, and missing-action states; only a valid pending answer can advance, while every other state produces an actionable Telegram notice instead of forwarding text to a Codex thread. These controllers are independent of polling and are unit tested using application-service fakes. `SessionManager` is the app-server-only Codex thread façade; its required `AppServerRuntime` interface exposes structured capabilities without adapter dispatch or optional-method casts. `AppServerAdapter` implements that interface over JSON-RPC and maintains the reconnecting transport, thread registry, turn coordination, interaction coordination, and event publication. `AppServerFailure` classifies timeout, transport loss, missing connection, connection-generation change, remote rejection, invalid state, and protocol defect across those boundaries. Remote error method, code, and data remain inspectable, but error strings and enumerable log fields omit request payloads and remote data. Durable Codex threads, live app-server attachments, and active turns are separate records; a thread keeps one stable local ID across detach and resume. Each transport has a persisted, monotonically increasing connection generation, and live attachments plus server-initiated requests are bound to that generation. `LegacyTmuxBridge` is a separate best-effort module invoked only by explicit `/tmux` commands. `Store` owns one SQLite connection and provides a compatibility façade over focused thread/attachment, interaction, notification/outbox, transcript/log, and runtime-state repositories. `RuntimeStateRepository` exclusively owns generic process KV and typed rate-limit persistence in `global_runtime`; `ThreadRuntimeRepository` exclusively owns token usage, progress, diffs, and goals in `token_usage` and `session_runtime`. The matching `Store` methods are stable delegates so callers can migrate incrementally. Repository objects are independently testable against an injected SQLite connection.

App-server stderr is reduced to connection-scoped byte and line diagnostics and is never copied into per-thread Event Logs. Runtime diagnostics redact sensitive structured fields, filesystem paths, and bot-token URLs before serialization.

Store transitions spanning Codex Thread and App-server Attachment state, Active Turn state, detach state, or Telegram action references commit in one SQLite transaction. `migrateDatabase` owns each schema-migration transaction; repository calls made by a migration participate in that transaction and do not open a nested transaction. Runtime-state repository writes are single-statement atomic operations.

Workspace selection canonicalizes the configured root and requested directory through the filesystem before containment checks. Picker and direct-command launches revalidate immediately before creating a Codex session and pass only the canonical contained directory downstream; missing, inaccessible, non-directory, and escaping paths fail with actionable messages that omit user-specific paths.

`RuntimeSupervisor` is the sole lifecycle owner. It starts the SQLite cleanup owner, eager app-server transport, adapter event forwarder, Telegram polling, Telegram event ingestion, delivery outbox worker, and action sweeper; waits for every critical loop; and stops them in reverse order exactly once. Rejection or unexpected completion of any critical loop records a durable fatal correlation, marks health failed, completes cleanup, and rejects the top-level wait so the process exits nonzero. Signal-driven stop uses the same idempotent path and exits cleanly.

`RuntimeHealth` owns the in-memory live snapshot and persists only the last fatal diagnostic. Overall health requires a running supervisor, connected app-server transport, and every critical subsystem in its running state. Reconnecting is degraded and a failed/dead control path is unhealthy. Telegram middleware records authorized update activity, the outbox records delivery successes and failures, and app-server telemetry includes transport, child PID when available, connection generation, reconnect attempt, and last message time. Command/callback failures return a correlation ID without exposing internal details; callbacks receive a prompt acknowledgement while slow work continues.

App-server and tmux do not share an interface: they have different identity, lifecycle, interaction, and failure semantics. The core interface is mandatory and app-server-specific. The legacy bridge exposes pane listing, attachment, probing, bounded incremental capture, sending, and interrupt operations against `LegacyTmuxAttachment`; it does not emit structured Codex events or create app-server pending actions from parsed terminal text. Capture stores legacy-only observations with pane identity, position, content hash, confidence, and reason. Pane enumeration isolates malformed records and panes that disappear during preview capture. Legacy command failures are classified and logged at a sanitized boundary; only proven pane disappearance, death, or identity replacement makes an attachment stale, while transient command failures remain retryable. Submit fallback ordering deduplicates equivalent tmux key sequences before advancing. A missing tmux binary therefore affects only an explicit fallback command, never normal construction or startup.

The app-server boundary has a deterministic fake transport for lifecycle scenarios. Its diagnostics retain message order, direction, and connection generation so reconnect and stale-message failures are reproducible without Telegram or a live Codex process. A compact checked contract fingerprints the generated client requests, server requests, notifications, and critical lifecycle shapes from a named Codex CLI version. `npm run contract:check` compares an installed CLI with that fixture; intentional upgrades use `npm run contract:refresh` and require protocol review. `/doctor` and CI diagnostics report the checked version.

## State

SQLite tables:

- `schema_migrations`: ordered migration version, name, and application time. Every migration runs in its own transaction; startup stops with the failing version and rollback context. A database newer than the running binary is rejected before journal-mode changes or migrations.
- `codex_threads`: durable app-server thread identity and local metadata, unique by Codex thread ID.
- `appserver_attachments`: current attachment status and connection generation for a durable thread.
- `active_turns`: the currently running Codex turn, separate from durable thread and attachment state.
- `sessions`: temporary compatibility migration source; old app-server and PTY rows are moved out and the mixed-schema table is then removed.
- `legacy_tmux_attachments`: tmux target, owning chat, input/probe state, pane identity, and the bounded last-seen capture boundary; it cannot contain Codex thread, turn, or connection-generation state.
- `legacy_tmux_observations`: deduplicated fallback-only output, diagnostics, and heuristic interaction warnings. These rows never participate in core pending actions, logs, transcripts, routing, or notifications.
- `pending_actions`: approval/question requests, their owning app-server generation, and their `pending`, `submitting`, confirmed, orphaned, or retryable-failure state.
- `event_log`: normalized operational diagnostics for `/log`; raw RPC bodies, Transcript output, approval answers, workspace paths, bot-token URLs, and tmux input are excluded.
- `transcript_chunks`: bounded Codex output chunks for `/transcript`, keyed by turn, item, and chunk index with explicit finalization. Small streaming deltas update the current item chunk instead of creating one row each.
- `callback_tokens` and `interaction_drafts`: short Controller/chat-bound Telegram controls and restart-safe wizard state. Tokens carry operation, resource kind and identity, expiry, and expected resource state; durable claim metadata prevents concurrent execution. Successful controller work commits a claim, transient failure releases it, and startup releases claims abandoned by a stopped process. `user_id` is mandatory.
- `routing_composes` and `sticky_routes`: restart-safe one-shot compose selections and explicit per-chat/user sticky routes.
- `session_chats` and `telegram_thread_messages`: thread delivery audiences and bot-message associations used for reply routing.
- `notification_outbox`: at-least-once high-signal Telegram delivery; retryable rows retain their delivery payload and delivered rows scrub it immediately.
- `session_runtime` and `global_runtime`: plans, diffs, goals, limits, and recovery metadata.
- `action_messages`: Telegram messages associated with pending requests so keyboards can be invalidated.

The bridge can restart and retain thread metadata. Legacy app-server rows are grouped by Codex thread ID; the newest row becomes canonical and transcripts, logs, pending actions, usage, progress, goals, diffs, and the last-active pointer are reparented transactionally. Old PTY rows with tmux targets migrate to `legacy_tmux_attachments`; managed PTY rows are discarded because managed PTY mode no longer exists. Persisted app-server attachments and turns are not treated as live after restart. App-server threads can be manually resumed through Telegram session controls, and `/resume` can query Codex history directly. Legacy tmux attachments stay outside core session listing, routing, approvals, transcripts, and recovery cards.

Schema evolution is numbered: the legacy baseline is version 1, thread/session normalization from #2 is version 2, scoped routing and callback claims are version 3, bounded transcript/maintenance support is version 4, durable legacy tmux capture boundaries are version 5, owned Interaction Controls are version 6, and sensitive terminal-data scrubbing is version 7. Migration 6 invalidates unowned callback tokens, makes Controller ownership mandatory, records resource identity/version, removes local `session_grants`, and removes the unused pending-action nonce. Migration 7 clears legacy Event Logs that may contain raw protocol data and scrubs terminal pending-action, callback, draft, and delivered-outbox payloads. Unversioned databases run through the same idempotent baseline and transactional transformations as new databases; there is no separate ad hoc startup mutation path.

Routine hourly maintenance removes expired or consumed callback controls, completed drafts, old sent outbox rows, stale logs and legacy tmux observations, and old resolved/orphaned actions. It preserves pending/submitting/retryable actions and any action referenced by an undelivered notification. Transcript deletion is opt-in through `TELE_CODEX_TRANSCRIPT_RETENTION_DAYS`; when unset, Transcripts are preserved indefinitely. The configured day window is applied to finalized Transcript chunks on every maintenance tick. SQLite checkpoint support is explicit, while `/doctor` and `/health` report the schema version, database size, WAL size, and excessive-size warnings.

`/kill` is the sole public command for interrupting an Active Turn. Its internal interrupt operation requires a connected current-generation App-server Attachment whose generation matches both the adapter registry and persisted thread state, plus the same proven Active Turn in volatile and persisted state. Disconnected, reconnected-but-unattached, stale-attachment, missing-turn, and timeout outcomes fail visibly; a confirmed interruption clears the turn and leaves the attachment idle, while an actual failed turn leaves it in error. `/detach` removes the live attachment, `/archive` archives the durable Codex thread, and `/forget` removes local tele-codex metadata without deleting Codex history. No record is an implicit send target. `/send` creates a five-minute, one-message compose route; its opaque picker tokens are scoped to chat, user, thread identity, expiry, and the thread version observed when the picker opened. Workspace, resume, model, and process pickers use the same opaque persisted-token contract and never invalidate another picker message when a newer picker opens. Direct `/send`, replies to associated agent messages, and an explicit `/use` sticky route are the other accepted text-routing paths. Detached app-server threads selected explicitly are resumed before composing; archived, removed, stale-version, stopped, and paused targets fail visibly. `/sessions` and all routing surfaces contain Codex threads only. Legacy tmux uses `/tmux` controls whose opaque callback tokens are scoped to chat, user, operation, attachment, expiry, and expected attachment version. `/tmux capture` compares a maximum 200-line/64-KiB pane snapshot with the persisted boundary; unchanged and overlapping scrollback is ignored, and ambiguous same-position redraws are skipped. Pane ID/PID replacement or disappearance marks the attachment stale. `/tmux interrupt` only writes Ctrl-C to an identity-checked external pane and never claims process ownership.

## Notification Strategy

High-signal events for all sessions are committed to the SQLite outbox before delivery:

- approval requests
- questions
- task completion
- errors
- blocked states

Transient durable-delivery failures use capped exponential backoff; repeated failures are visible through `/health` and can be requeued. Once a Telegram chat routes input to a thread, subsequent agent output and interactions for that thread are scoped to its associated chat set instead of broadcast as process-global active-session output. Streamed agent messages retain independent in-memory buffers per chat, fan out concurrently, and retry each failed chat up to three times with exponential delay before an explicit drop; successful chats are never replayed because another chat failed. Streamed messages retain their Telegram message-to-thread association so a reply returns to the originating thread. Transcript streaming remains best-effort and never enters the durable outbox, but its buffer is flushed before a durable completion notification. Full output is persisted for `/transcript`.

## Approval Strategy

App-server interactions are answered through typed JSON-RPC responses. Telegram callback data carries only a short random token; the action, decision, Controller, intended chat, expiry, target identity, and payload stay in SQLite. Claiming an action is transactional, so duplicate or cross-chat callbacks cannot submit it twice. A successful transport write moves an action to `submitting`; only the matching `serverRequest/resolved` notification from the same connection generation marks it resolved. Retryable write failures release the claim, retain a usable callback control, and appear through `/pending`. Public raw `/approve` and `/deny` commands do not exist. Native session-level approval is shown only when explicitly enabled; tele-codex does not maintain a parallel local grant store. Secret questions are never collected through Telegram.

## Reconnection

Telegram long polling resumes through Bot API update offsets managed by `grammY`. JSON-RPC requests have bounded waits. A candidate App-server generation becomes current only after the `initialize` response and `initialized` notification both succeed. Initialization failure closes the half-open transport, leaves its traffic stale, and enters the same supervised reconnect loop as later transport loss; exhaustion rejects the eagerly observed adapter runtime promise exactly once and preserves failed health through cleanup. Transport messages and close events carry their connection generation, so delayed events from an older child process or socket cannot mutate a newer connection. Transport loss clears only attachments and Active Turns from the lost generation, orphans its unresolved requests, invalidates their Telegram controls, and tells the user to resume the thread and retry the original command. Reconnection alone does not rehydrate an attachment or turn; explicit resume creates a current-generation attachment, and only a new `turn/start` response or `turn/started` notification proves an Active Turn. Reconnect uses capped exponential delay and a bounded attempt budget; recovery resets the budget, while exhaustion fails the supervised transport so systemd can restart the complete runtime. App-server threads are resumed only after explicit Telegram selection. The user service provides restart-on-failure and control-group cleanup; `service update` builds before restart and requires a stable active PID afterward. Legacy tmux attachments persist separately but remain heuristic and best-effort.

## Known Risks

- Codex app-server is experimental and may change protocol fields or control method shapes.
- JSON-RPC over stdio is assumed to be newline-delimited; verify against the installed Codex version before relying on it operationally.
- Legacy tmux capture and input submission are heuristic and require local verification.
- Session-level grants reduce friction but increase blast radius.
